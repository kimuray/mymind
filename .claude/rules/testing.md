# テストのルール

## どこで何を確かめるか

| 層 | 道具 | 確かめること |
|---|---|---|
| `packages/domain` | Vitest | 業務日、遷移表、自動ルール、集計。分岐をすべて通す（カバレッジの目標は90%以上） |
| `packages/db` / `apps/server` | Vitest ＋ インメモリ SQLite | リポジトリとAPIの結合。トランザクションの一貫性、検証エラー、セキュリティのミドルウェア |
| `packages/agent` | Vitest ＋ 出力例のファイル | 入力の組み立て、出力の検証、再試行の判断。実物のエージェントは呼ばない |
| 画面 | Playwright ＋ 偽のエージェント | 主要な操作の流れ |

## 書き方

テストの `describe` には、対応する要件IDを含めます（例：`describe('FR-T03 ステータス遷移', ...)`）。1つのテストでは1つの振る舞いだけを確かめ、テスト名にはその振る舞いを日本語で書きます。

時刻に依存するテストでは、現在時刻を固定値で渡します。境界値（業務日の切り替え時刻の直前と直後、月末、年末）を必ず含めます。

エージェントの出力を扱うテストでは、`packages/agent/fixtures/` に出力例を置いて読み込みます。正常な例だけでなく、コードブロックで囲まれた出力、値の範囲外、余計な項目がある出力など、実際に起きうる崩れ方の例も用意します。

## してはいけないこと

- CI で実物の LLM やエージェントを呼ぶ
- テストを通すために、テストを削除する、`skip` にする、期待値を実装に合わせて書き換える
- 実データのディレクトリを読むテストを書く
- 実行順序に依存するテストを書く
