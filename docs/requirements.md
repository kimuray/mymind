# 要件定義

## 1. 目的

mymind は、毎日の「計画 → 実行 → 振り返り」を習慣にするための個人用TODOツールです。単なるタスク管理ではなく、振り返りを通じた学習、感情のアウトプット、思考の整理を目的とし、ローカルのAIエージェントからのフィードバックでその振り返りを深めます。

利用者は開発者本人の1人だけです。PCのブラウザから `127.0.0.1` で使い、AIにはAPIではなく、手元のClaude CodeやCodexを使います。

## 2. 設計原則

**事実は自動で残し、書くのは考えたことだけ。** 着手日、完了日、持ち越し回数、状態が止まっていた期間は操作ログから自動で記録します。ユーザーが書くのは振り返りの文章だけです。

**習慣化の最低ラインを低くする。** 振り返りは一行でも保存できます。完璧な日より、途切れない日を優先します。

**時間帯に応じて、次の行動をアプリが示す。** 朝は計画、夜は振り返りへの導線を前面に出します。

**操作は少なく、キーボードで完結させる。** 主要な操作はすべて1〜2打鍵で行えるようにします。

**AIは明示的に呼ぶ。** FBは自動生成せず、ユーザーがボタンで依頼したときだけ生成します。

## 3. 機能要件

### 3.1 タスク

| ID | 要件 |
|---|---|
| FR-T01 | タスクを追加できる。追加先は操作している画面で決まり、今日の画面なら今日の計画に、バックログ画面ならバックログに入る |
| FR-T02 | タスクを親子で管理できる。深さは2階層（親と子）まで |
| FR-T03 | タスクは「未着手・着手中・中断・待ち・完了・中止」の6つのステータスを持つ。遷移可能な組み合わせは architecture.md の遷移表に従う |
| FR-T04 | ステータスが変わるたびに、変更前後のステータスと時刻を履歴として記録する |
| FR-T05 | タスクを「今日」「明日」「バックログ」の間で移動できる |
| FR-T06 | 着手中のタスクをバックログに移動したら、自動で中断にする。取り消し操作を提示する |
| FR-T07 | 子タスクが着手されたら、未着手の親タスクを自動で着手中にする |
| FR-T08 | 子タスクがすべて完了したら、親タスクの完了を提案する。自動では完了にしない |
| FR-T09 | タスクのタイトルとメモ（Markdown）を編集できる |
| FR-T10 | 今日の計画内とバックログ内で、タスクを並べ替えられる |
| FR-T11 | 中止したタスクは削除せず、「やめると決めた」記録として残す |
| FR-T12 | 各タスクに「着手から何日目か」を表示する |

### 3.2 1日の流れ

| ID | 要件 |
|---|---|
| FR-D01 | 日付の切り替えは業務日で扱う。初期値は5:00で、設定から変更できる |
| FR-D02 | 朝の計画画面で、前日のFBと調子を表示する |
| FR-D03 | 朝の計画画面で、前日の計画にあって未完了のタスクを一覧し、「今日もやる」「バックログへ」「実は終わった」のいずれかを選べる |
| FR-D04 | 朝の計画画面で、バックログから今日やるタスクを選べる |
| FR-D05 | 朝の計画はまとめて一度に確定する。途中で画面を離れても、確定前の状態はデータに反映しない |
| FR-D06 | 振り返り画面で「思考の整理」と「学び」をMarkdownで書ける。書く画面とプレビューを切り替えられる |
| FR-D07 | 振り返り画面の冒頭に、その日の完了・着手・状態変化を操作ログから自動でまとめて表示する |
| FR-D08 | 振り返りは「保存のみ」と「保存してFBをもらう」のどちらでも保存できる。一行だけでも保存できる |
| FR-D09 | アプリを開かなかった日（空白日）があっても、未完了のタスクが持ち越し候補から漏れない。持ち越しの基準は「今日より前で、最後に計画があった業務日」とし、空白日の日数を朝の計画画面に表示する（詳細は architecture.md 4.5） |

### 3.3 AIフィードバック

| ID | 要件 |
|---|---|
| FR-A01 | 日次FBは、ユーザーがボタンで依頼したときだけ生成する |
| FR-A02 | 日次FBには「よかったこと」「気づき」「明日の一手」と、5段階の調子（絶好調・好調・普通・不調・絶不調）とその根拠を含める |
| FR-A03 | ユーザーは調子を手動で修正できる。AIの判定と手動の値は両方記録する |
| FR-A04 | 同じ日のFBを再依頼できる。過去のFBは上書きせず履歴として残し、最新のものを表示する |
| FR-A05 | 振り返りはあるがFBのない過去の日について、後からFBを依頼できる |
| FR-A06 | 月次総括をボタンで依頼できる。月の途中で依頼した場合は「途中経過」として扱う |
| FR-A07 | 使うエージェント（Claude Code / Codex）を設定で選べ、依頼時にも切り替えられる |
| FR-A08 | 生成中は進捗を表示し、キャンセルできる。失敗したら理由の要約と再試行の操作を表示する |
| FR-A09 | FBを依頼していない日は、調子を空欄とし、マメを「おやすみ中」の表情で表示する |
| FR-A10 | FBに含まれる数値（日数、件数など）はコードで計算した値を使い、AIには計算させない |
| FR-A12 | FB と総括を依頼する前に、エージェントに送る内容を「送信内容を見る」で確認できる。表示する内容は実際に送る内容と完全に一致させ、切り詰めなどの加工があればその箇所と理由を示す。設定で「依頼の前に毎回確認する」を選べる |
| FR-A11 | FBはコーチとして、利用者に新しい観点や気づきを与えることを目的に書く。共感と受容を土台にしつつ、同じパターンの繰り返しや、決めたことの未実行などには率直に指摘する。方針は `prompts/coaching-policy.md` に従う |

### 3.4 記録と見直し

| ID | 要件 |
|---|---|
| FR-R01 | タイムラインで、タスクごとの着手中・中断・待ち・完了の期間を横棒で表示する。表示期間は1週間・2週間を切り替えられる |
| FR-R02 | タイムラインに日ごとの調子（マメ）を並べて表示する |
| FR-R03 | タイムラインでタスクを選ぶと、着手中・中断・待ちの日数の内訳を表示する |
| FR-R04 | カレンダーで日ごとの調子と完了件数を表示し、日付を選ぶとその日の記録（完了、状態変化、振り返り、FB）を表示する |
| FR-R05 | カレンダーで月の総括（最新のもの）を表示する |
| FR-R06 | 最後に触れてから一定日数（初期値30日、設定で変更可）経ったバックログのタスクを「棚卸し」として一覧し、「今週やる」「残す」「中止」のいずれかを選べる |
| FR-R07 | 日付ごとの詳細に「記録を再生成」ボタンを置く。押すと、その日の記録（完了・着手・状態変化のまとめ、タイムラインの区間、集計値）をイベントから作り直す。記録の不整合に気づいたときのフォールバックとして使う。再生成後にFBを再依頼するかは選べる |

### 3.5 通知

| ID | 要件 |
|---|---|
| FR-N01 | 朝の設定時刻に、その日の計画がまだ確定していなければデスクトップ通知を出す |
| FR-N02 | 夜の設定時刻に、その日の振り返りがまだ保存されていなければデスクトップ通知を出す。通知文には完了件数や長引いているタスクなど、その日の事実を含める |
| FR-N03 | 日曜の夜に、棚卸しの対象があればデスクトップ通知を出す |
| FR-N04 | 通知は種類ごとにオン・オフと時刻を設定できる。同じ種類の通知は1日1回まで |
| FR-N05 | 通知をクリックすると、該当する画面をブラウザで開く |

### 3.6 操作

| ID | 要件 |
|---|---|
| FR-U01 | 主要な操作をキーボードで行える。割り当ては DESIGN.md のキーマップに従う |
| FR-U02 | `⌘K` でコマンドパレットを開き、画面移動や操作を検索して実行できる |
| FR-U03 | `?` で、その画面で使えるキーの一覧を表示できる |
| FR-U04 | 画面は「ナビゲーション・メイン・詳細」の3ペインで構成する |

## 4. 非機能要件

| ID | 分類 | 要件 |
|---|---|---|
| NFR-01 | 動作環境 | macOS上のNode.js（LTS）で動作する。対応ブラウザは NFR-17、対応OSは NFR-27 |
| NFR-02 | セキュリティ | サーバーは `127.0.0.1` のみで待ち受け、外部のWebページからの操作を受け付けない（詳細は architecture.md） |
| NFR-03 | 応答性 | タスクの操作は、通信を待たずに画面へ即時反映する |
| NFR-04 | 耐久性 | DBのスナップショットを1日1回、DBとは別の場所に保存する |
| NFR-05 | プライバシー | データはローカルのSQLiteファイルに保存する。FB依頼時のみ、振り返りとタスクの情報がエージェント経由でAIの提供元に送られることをユーザーが理解できるようにする |
| NFR-06 | アクセシビリティ | 本文のコントラスト比4.5:1以上、キーボードフォーカスが常に見える、アイコンのみのボタンにラベルを付ける |
| NFR-07 | 保守性 | ドメインのルールはDBやHTTPに依存しない純粋関数として実装し、単体テストで検証する |
| NFR-08 | 移植性 | DBアクセスとエージェント起動はインターフェースの裏に隠し、将来のクラウド版（D1など）へ差し替えられるようにする |
| NFR-09 | 記録の粒度 | 記録は業務日の単位で扱う。時刻はイベントの順序を決めるためだけに保存し、画面の表示、集計、FB の入力には使わない。イベントの時刻を訂正する機能は持たない |
| NFR-10 | フォント | Inter と Noto Sans JP はアプリに同梱して自前で配信する。外部のフォント配信サービスに依存しない。和文フォントは使う文字に絞ってサブセット化する |
| NFR-11 | オフライン | FB と総括の生成（エージェント）以外のすべての機能が、外部との通信なしで動作する |
| NFR-12 | 下書きの保護 | 振り返りとタスクのメモの書きかけを、入力が止まってから1秒後にブラウザの IndexedDB に自動保存する。保存に成功したら下書きを消す。保存前にタブを閉じたりサーバーが止まったりしても、次に開いたときに下書きの復元を提示する |
| NFR-13 | 画面間の一貫性 | 複数のタブで開いていても、あるタブでの変更が他のタブに反映される（ADR-0008）。同じタスクを古い画面から更新しようとした場合は、更新を拒否して再読み込みを促す |
| NFR-14 | 業務日の切り替え検知 | 入力系の操作（キー入力、クリック、フォーカス）のたびに、画面が表示している業務日と現在の業務日を比較する。変わっていたら操作を止め、「今日の画面へ移る」か「前の日の記録として続ける」かを選ばせる。サーバーも、画面が想定する業務日と現在の業務日が異なる更新を、明示の指定がない限り拒否する |
| NFR-15 | AI への送信データ | エージェントに渡すデータは FB に必要な項目に限り、1回あたりの量に上限を設ける。月次総括は日ごとの要点を段階的にまとめて渡し、振り返りの全文をまとめて送らない（architecture.md 16章）。送信内容の確認は FR-A12 で提供する。除外や置き換えの機能は将来、送信前処理の段階を追加して実現する |
| NFR-16 | 機微データ | 振り返り、メモ、FB、エージェントの入出力を機微データとして扱い、クラウドに置いた場合を基準に保護する（ADR-0009）。ログに出さない、ファイルのパーミッションを 600 にする、暗号化の差し込み口を通して読み書きする、エージェントの入出力ログは30日で削除する |
| NFR-17 | 対応ブラウザ | デスクトップ版 Chrome の最新安定版をサポートする。それ以外のブラウザは動作を保証しないが、Chrome 独自の API には依存しない |
| NFR-18 | 性能【暫定】 | 5年分のデータ（タスク1万件、イベント10万件、振り返り1,800日分）で、操作から画面への反映が100ms以内（楽観的更新）、ローカル API の応答が95%の要求で50ms以内、初回表示が1.5秒以内、2週間のタイムラインの表示が200ms以内 |
| NFR-19 | 常駐時の負荷【暫定】 | 待機中のサーバーのメモリ使用量が150MB以下で、CPU をほぼ使わない。定期処理は必要な時刻にだけ動かす |
| NFR-20 | 二重起動の防止【暫定】 | 同じデータディレクトリを使うサーバーは1つだけ起動できる。ロックファイルで検出し、2つ目は理由を表示して終了する |
| NFR-21 | 状態の見える化【暫定】 | `GET /api/health` と設定画面で、エージェントの利用可否、最後のバックアップの日時と結果、DB のサイズ、直近の FB 生成の失敗を確認できる |
| NFR-22 | 透明度と動き【暫定】 | OS の「透明度を下げる」「視差効果を減らす」の設定（`prefers-reduced-transparency`、`prefers-reduced-motion`）に従い、ガラスの面を不透明な面に、アニメーションを最小限に切り替える。コントラストは E2E で自動検査する |
| NFR-23 | バックアップの復元目標【暫定】 | 失うデータは最大24時間分まで（1日1回のスナップショットと、マイグレーション前の自動スナップショット）。スナップショットは作成時に整合性を検査し、14世代を残す。復元手順を文書化し、実際に復元できることを確かめる |
| NFR-24 | ログ【暫定】 | 構造化ログ（JSON）で出力し、14日でローテーションする。機微データの項目は自動で伏せ字にする |
| NFR-25 | バージョンとマイグレーション【暫定】 | アプリにセマンティックバージョンを付け、変更履歴を残す。マイグレーションは前進のみとし、失敗した場合は直前のスナップショットから戻す |
| NFR-26 | 依存関係の安全性【暫定】 | CI で依存関係の脆弱性を検査し、重大度 high 以上があれば失敗させる。依存関係の更新は Dependabot で行い、人がレビューする |
| NFR-27 | 対応OS | 常駐と通知は macOS のみを対象とする。CI は Linux で動かすため、OS に依存する処理（launchd、通知、キーチェーン）はアダプタに閉じ込める |
| NFR-28 | ライセンス表記 | 同梱するフォントや依存関係のライセンスを、設定画面から確認できるようにする |

## 5. 暫定決定（レビュー待ち）

次の事項は、実装を止めないために暫定的に決めたものです。エージェントはこの内容で実装してよく、Yoshihiro のレビューで変わった場合は issue を通じて修正します。詳細は各 issue を参照してください。

| 事項 | 暫定決定の要点 | issue |
|---|---|---|
| 親子関係の境界ケース | 親の移動・中止・完了は未完了の子に波及（中止と完了は確認あり）。子だけを今日に入れても親は計画に入れない。3階層目は作れない | 009 |
| 削除と取り消し | 削除は作成した業務日のうちだけ。`⌘Z` で直近20件まで、逆向きのイベントを追加して取り消す | 010 |
| 画面のURL | `/`、`/morning`、`/reflection/:day?`、`/backlog`、`/timeline`、`/calendar/:ym/:day?` | 011 |
| 対象外の機能 | 期日、繰り返し、タグ、全文検索、ダークモードは対象外（6章） | 012 |
| レビューの地点 | domain のルール、スキーマ、プロンプト、セキュリティ、文書とハーネスの変更は人のレビュー必須。判定はスクリプトで行う | 023 |

## 6. 対象外（現時点）

スマホ対応、インターネット経由の利用、複数ユーザー、クラウド同期、LLMのAPIを直接呼ぶ実装、FBの自動生成、期日、繰り返しタスク、タグ、全文検索、ダークモードは、現時点では対象外とします（期日以降の5つは暫定、issue 012）。将来スマホから使いたくなった場合は、まずTailscaleなどで手元のサーバーに接続する方法を検討し、PCが閉じていても使いたくなった時点でクラウド版を検討します。

## 7. 用語

| 用語 | 意味 |
|---|---|
| 業務日 | 日付の切り替え時刻（初期値5:00）を基準にした「その日」。深夜1時の操作は前日の業務日に属する |
| 計画 | ある業務日に「今日やる」と決めたタスクの集まり |
| バックログ | どの日の計画にも入っていない、覚えておくだけのタスク |
| 持ち越し | 前日の計画にあって未完了のタスクを、今日の計画に入れ直すこと |
| 着手期間 | 最初に着手してから、完了または中止になるまでの期間。中断や待ちの期間も含む |
| 調子 | その日の気持ちの状態を表す5段階の評価。振り返りの文章からAIが判定し、ユーザーが修正できる |
| マメ | 調子を表すキャラクター。表情と頭の芽の状態で5段階を表す |
| FB | 日次フィードバック。振り返りをもとにエージェントが生成する |
| 総括 | 月次の振り返り。日次の記録とFBをもとにエージェントが生成する |
| 棚卸し | 長期間触れていないバックログのタスクを、残すか中止するか判断する作業 |
