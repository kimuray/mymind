# ADR-0008：画面へのリアルタイム通知は SSE ＋ BroadcastChannel にする

- ステータス：採用
- 日付：2026-09-22

## 背景

サーバーから画面へ知らせたい出来事が2種類あります。1つは FB 生成ジョブの進捗、もう1つは他のタブや MCP 経由の操作によるデータの変更です（NFR-13）。方式として SSE と WebSocket を比較しました。判断の基準は、今の localhost 構成で素直に作れることと、将来クラウド（Cloudflare Workers）へ移したときに作り直しが小さいことです。

## 比較

| 観点 | SSE | WebSocket |
|---|---|---|
| 通信の向き | サーバー → 画面の片方向 | 双方向 |
| 今回の用途との一致 | 一致（画面からの操作は通常の HTTP API で送る） | 双方向の能力は使わない |
| 実装 | 通常の HTTP の GET。Hono に SSE 用のヘルパーがあり、Node と Workers の両方で動く | 接続の確立方法がランタイムごとに異なる |
| 再接続 | ブラウザの EventSource が自動で再接続し、`Last-Event-ID` で取りこぼしを補える | 自前で実装する |
| セキュリティ | 読み取り専用の GET なので、ADR-0007 の検証（状態変更時のトークン）とそのまま両立する | 接続時の認証を別に設計する |
| クラウド移行時 | 複数の接続に配信するには調停役（Durable Objects など）が必要 | 同じく調停役が必要。Durable Objects の休止機能と相性がよい |

どちらの方式でも、クラウドで複数の端末に配信するには調停役が必要になる点は同じです。今の用途は片方向で足り、SSE の方が実装・再接続・セキュリティのすべてで単純です。

## 決定

- **同じブラウザ内のタブ間**の同期には、サーバーを介さない `BroadcastChannel` を使う。あるタブで変更が成功したら、他のタブにクエリの無効化を通知する
- **サーバーから画面へ**の通知（ジョブの進捗、MCP など画面以外からの変更）には SSE を使う。エンドポイントは `GET /api/events` の1本にまとめ、イベントの種類で区別する
- 画面側は `RealtimeChannel` という薄いインターフェースを通して購読し、SSE の詳細を画面のコードに漏らさない

## 結果

将来クラウドへ移して複数の端末に配信する必要が出た場合は、`RealtimeChannel` の実装を Durable Objects を使った方式（SSE のまま、または WebSocket）に差し替えます。画面のコードとイベントの種類の定義は変えずに済みます。
